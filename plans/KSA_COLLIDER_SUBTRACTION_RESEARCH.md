# Primitive subtraction and hollow colliders in KSA

**KSA can represent collision geometry with holes, but the inspected build does not expose primitive subtraction, and its bundled Bepu implementation has no built-in subtractive shape.** The practical approach is to construct the remaining material as several convex colliders, or to generate a triangle surface and integrate it through an appropriate mesh path. For vessel parts, several ordinary collider modules are the closest fit to the existing engine. For body-fixed scenery, Sphinx already contains a direct Bepu mesh integration. [1][2][3][4]

| Desired capability | Finding | Practical consequence |
|---|---|---|
| Declare “box minus cylinder” in stock part XML | Unsupported by the inspected collider schema | A geometry preparation step or new authoring feature is needed |
| Give a Bepu compound a negative child | No such field or operation in the bundled representation | Adding the cylinder creates another colliding solid |
| Make a doorway, frame, cavity, or hollow vessel part | Supported representation through multiple convex children | Surround the opening with boxes or separate convex hulls |
| Import one concave mesh as a stock part collider | Unsupported | The mesh template throws; the exposed hull template convexifies the vertices |
| Use a mesh with openings as body-fixed scenery | Existing implementation in Sphinx | Select mesh collision and respect its geometry limits |
| Cut holes interactively at runtime | Feasible engineering direction, not existing support | Generate replacement convex pieces or triangles, then safely rebuild colliders |
| Implement exact analytic CSG collision tests inside Bepu | Possible in principle, substantial new collision work | No evidence supports treating this as a small KSA patch |

**Evidence baseline.** These conclusions concern KSA build `2026.9.7.5402`, identified by the local `current/version.json`, in the game-assemblies checkout at commit `57e6040`. The repository scope document identifies this tree as authoritative; the older `decomp/ksa` location referenced by some instructions is absent in this checkout. The bundled decompiled Bepu sources are the primary evidence for available behavior. Current upstream documentation and a historical maintainer discussion provide corroboration, not a substitute for inspecting the bundled implementation. This report establishes source-level feasibility; native contact behavior was not exercised. [5]

**What “subtraction” means here.** Boolean difference keeps the points inside A and outside B. A cylinder cut through a box therefore needs the surviving outer faces, the cylindrical interior wall, and correctly connected edges around the openings. A collision engine must generate valid contacts against those new surfaces, including contacts with an object already inside the hole.

An additive compound instead collects solid children. Its occupied region can have gaps and cavities because material was never placed there. That can reproduce the useful result of subtraction without storing a subtraction operation. It is not necessarily a cleaned Boolean union at contact level: overlapping children retain their individual collision tests and can produce redundant contacts. In the bundled `CompoundChild`, the stored data is only position, orientation, and a shape index. There is no sign, negative-volume flag, or Boolean operator. The compound collision task enumerates overlapping children and dispatches their tests. [2][6]

The bundled built-in shapes are `Sphere`, `Capsule`, `Box`, `Triangle`, `Cylinder`, `ConvexHull`, `Compound`, `BigCompound`, and `Mesh`. `DefaultTypes.CreateDefaultCollisionTaskRegistry` registers their pair tests, including `BigCompound`–`Mesh` and `Mesh`–`Mesh`. Neither that registry nor the collider representation provides a CSG difference type. Bepu's API documentation separately defines convex shapes as having no hollowed-out regions. [3][7]

There is one potentially misleading name in the sources: `GJKDistanceTester.SampleMinkowskiDifference`. It subtracts support points from two shapes to help calculate their separation. A Minkowski difference is a set of vector differences, not the Boolean set difference that removes B's occupied volume from A. This method therefore does not provide a hole-cutting API. [8]

The Bepu maintainer addressed almost this exact proposal in the April 27, 2012 discussion *Constructive Solid Geometry Support*: ordinary convex-pair results do not contain the information needed to construct the contact manifold of a subtractive interior. He identifies compounds and meshes as alternatives. That discussion concerns an older engine generation; the absence of subtraction in this KSA build is independently supported by its bundled shape and collision-task code. [9]

**How a stock part becomes a collision shape.** The relevant path is:

`XML or GLB collider markers → ColliderModule.Template.Colliders → ColliderTemplate.Create(part) → ColliderModule.Handle → Vehicle.CreateColliderCompound → Bepu BigCompound → narrow-phase contacts`

1. `ColliderModule.Template.Colliders` is an XML-serialized list admitting exactly `Box`, `Capsule`, `Cylinder`, `Sphere`, and `ConvexHull`. There is no XML entry for a triangle mesh, subtractive shape, operation tree, or explicit nested compound. `CreateComponents` creates one module for every listed template, so multiple colliders per part are a normal supported arrangement. Stock structural content already includes a collider block containing two boxes. [1][10]
2. `ColliderTemplate.GetShape` lazily creates and caches a Bepu shape handle using KSA's shared shape registry. The template also supplies the authored location, orientation, and any shape-center correction. `ColliderModule` stores that handle and the owning part. [11]
3. `Vehicle.CreateColliderCompound` iterates the vehicle's collider modules, transforms each into vehicle assembly coordinates relative to the center of mass, and adds each handle as a child. It constructs a single `BigCompound` and records the child-to-part map. Thus ten convex colliders on one part become ten leaves of the vessel's existing compound; they do not require ten independent rigid bodies. [12]
4. The corresponding update functions refresh child handles, positions, orientations, bounds, and the tree. `CreateOrUpdateColliderCompound` rebuilds when the child count changes; ordinary updates assume one child for each collider module. [13]
5. `ConstraintSim.AddVehicle` attaches the shape to a dynamic body, using mass and inertia supplied by KSA. The builder's use of `AddForKinematic` and `BuildKinematicCompound` does **not** mean the vessel is kinematic: those methods assemble shape children without deriving the body's mass properties. The body is explicitly created with `BodyDescription.CreateDynamic`. [12][14]

This design is favorable for hollow parts. For example, an aligned rectangular opening through a slab can be represented exactly, apart from numerical tolerances, by four surrounding boxes. A U-shaped channel needs a base and two sides. A box with an enclosed rectangular cavity can be partitioned into six solid slabs, provided the dimensions and placement leave the intended void. These are geometric constructions inferred from the supported representation, not already authored KSA assets demonstrated in this investigation.

A circular hole requires an approximation when built from finite ordinary convex pieces: a collection of hull wedges can follow its inner wall with a polygonal cross-section. Increasing the number of wedges improves the fit but increases collision work. For moving concave objects, Bepu's performance guidance favors a small compound of simple shapes and advises keeping hull and mesh complexity low. No KSA-specific safe maximum or performance estimate has been established here. [15]

**A convex hull cannot preserve a cutout.** `ConvexHullColliderTemplate.EnsureBaseHull` calls `ScaledPoints`, then `ConvexHullHelper.CreateShape` on the resulting vertex positions. `ScaledPoints` reads positions from the referenced mesh. It does not preserve the mesh's triangle connectivity as collision surfaces. The computed hull encloses the point set, so a donut, doorway, or hollow shell submitted as one hull loses its concavity. Merely exporting a Boolean-cut visual mesh under one hull marker will therefore not preserve its hole. [16]

KSA's GLB importer recognizes `_ColPrim_Box`, `_ColPrim_Sphere`, `_ColPrim_Capsule`, `_ColPrim_Cylinder`, and `_ColPrim_Hull`. Unknown primitive markers are skipped with a warning. Each hull marker becomes one `ConvexHullColliderTemplate`; each genuinely convex piece needs its own marker. The marker and mesh-data names must match, and each collision mesh must contain one glTF primitive. Nothing in this path interprets a Blender Boolean modifier or a “negative” marker as an operation. The prepared output geometry must already be suitable for the selected collider representation. [17]

**The mesh class in KSA is an incomplete integration, not a hidden switch.** `MeshColliderTemplate.CreateShapeInto` throws `NotSupportedException` with the message “cannot be registered with Bepu yet.” Its derived `ConvexHullColliderTemplate` overrides that method, which explains why mesh-loading infrastructure exists while general triangle-mesh part colliders remain unavailable. The XML type list also omits `Mesh`. Changing only the throwing method would leave additional schema and compound-structure problems unresolved. [1][18]

**The compound-child restriction matters.** The bundled `Compound.ValidateChildIndex` returns false for shape batches marked `Compound`. Both ordinary compound batches and homogeneous compound batches set that flag; `Mesh` uses the latter. Current upstream source makes the intended invariant explicit: children must be convex. The stock layout therefore cannot be extended by simply assigning a nested `BigCompound` or `Mesh` handle to one part's `ColliderModule`. [19]

This is a supported-representation restriction, not a promise that release builds will catch every misuse cleanly. In fact, the inspected `ValidateChildIndices` loops over individual validation calls without propagating their returned failures. A handle accepting assignment is not evidence that subsequent collision processing supports the layout. The appropriate solution for a part made of multiple pieces is to flatten them into the existing vessel compound, preferably through separate collider modules. [19][12]

**Bounding boxes do not inherently close the opening.** With authored colliders, `Vehicle.UpdateCollisionGeometry` computes overall box and sphere bounds from the compound. Those bounds enclose the whole object, including its holes, but the actual collider remains the `BigCompound`. A broad-phase overlap can therefore proceed to child tests that find no contact in the empty region. If the vehicle has no authored collider modules, the alternate path creates a compound containing a bounding-box collider; that fallback really does fill openings. Another positive collider overlapping a planned hole will also continue to block it. [20]

**Static scenery has two distinct paths.** Stock `StaticObject.BuildCollisionShape` consumes the same collider templates, combines the object and subobject colliders, and creates a `BigCompound`. Native static content can therefore use the same multi-piece construction, with the same lack of subtractive operations. It does not automatically turn an arbitrary visual mesh into a general mesh collider. [21]

Sphinx already implements the more flexible alternative in this repository. `StaticCollider.Build` reads the imported triangle geometry, applies the placement transform, creates a Bepu `Mesh`, and registers it directly in the shared shape registry. `SphinxPhysics.Sync` uses that mesh as the top-level shape of a Bepu static in each relevant physics bubble. It bypasses `MeshColliderTemplate` and does not put the mesh inside a vessel compound. This resolves the apparent contradiction between KSA's unsupported mesh template and Sphinx's existing mesh collision implementation. [4][22]

For a hollow building or tunnel above the terrain, a prepared surface mesh can therefore preserve openings through the existing Sphinx implementation. Sphinx duplicates triangle winding so surfaces collide from both directions; this creates two-sided surface tests, not a volumetric Boolean solid. The interior walls and all other desired surfaces still have to exist in the imported mesh. A thin surface also remains thin: robustness against fast motion or deeply embedded bodies requires contact testing. [4]

Sphinx's operational limits matter specifically for holes. Explicit Mesh rejects inputs over 100,000 source triangles. Auto falls back to a fitted box above that limit, and the fallback explicitly warns that it blocks openings. The total budget is 500,000 retained geometric triangles across placements; the implementation stores two Bepu triangles per retained triangle for the two windings. These are mod limits, not general limits imposed by Bepu. The project README still lists native contact acceptance as outstanding, so the existing source demonstrates an implemented integration rather than a newly verified live result. [4][23]

Adding a raw static handle alone is insufficient in KSA. `NarrowPhaseCallbacks.AllowContactGeneration` admits recognized clutter or a vehicle's known ground surfaces, and rejects other dynamic-static pairs. Sphinx extends this filter only for its owned simulation/handle pairs and also extends ground-surface classification. It maintains bubble-relative poses, updates after origin snaps, and detaches handles before simulation pooling or disposal. A future generated static mesh should reuse that lifecycle rather than bypass it. [22][24]

**What a future subtraction feature would need.** The most compatible design is an authoring operation whose output is ordinary supported geometry. An implementation could retain a description of a base solid and cutters, calculate the remaining material when edits are committed, and produce one of two outputs:

| Target | Generated result | Integration strategy |
|---|---|---|
| Vessel part | Small set of convex solids | One collider module per piece; let KSA build the vessel compound |
| Body-fixed scenery | Triangle surface, or simple convex pieces | Replace an owned top-level mesh through the Sphinx lifecycle, or author native static collider pieces |

For aligned box cuts, direct geometric partitioning can produce a small exact box decomposition. General rotated or curved cuts need a more substantial geometry algorithm: triangulate the Boolean result and decompose it into convex pieces for a vessel, or retain a suitable triangle surface for a static. Convex approximation must preserve useful clearances; an algorithm that bridges a narrow tunnel would defeat the purpose. No Boolean or decomposition package was selected or validated by this research.

Runtime updates add KSA-specific obligations even when the generated geometry is valid:

- **Safe mutation and ownership.** KSA explicitly forbids shape-registry mutation while the vehicle update is stepping. Changes need the frame synchronization point and the appropriate shape unlock. Cached template handles can be shared; scaled module shapes have separate ownership. Allocate the replacement, detach old references safely, and only then dispose owned shapes. Existing Sphinx lifecycle code and Godzilla's collider documentation provide relevant precedents. [11][25][26]
- **Topology and contact identity.** If one collider becomes several, rebuild the module-to-child relationship, compound bounds, and `ColliderParts` map together. KSA uses child indices to identify contacted parts, record structural contact loads, and detect docking events. A bare list of new Bepu leaves without the corresponding part map is incomplete. [12][13][27]
- **Scaling and offsets.** Hull creation recenters its points and returns an offset that KSA compensates for. The generated hull must use that convention. Runtime `ScaleFactors(double3)` collapses XYZ scaling to the largest axis for these scale-aware modules; an accurately cut nonuniform shape cannot assume native runtime collider scaling preserves its intended proportions. [16][28]
- **Physical properties.** Cutting collision geometry does not automatically remove mass or propellant capacity. KSA sums mass modules and separately copies its own mass and inertia into Bepu. A tool that claims to remove actual material must make an explicit decision about physical properties. A collider-only tool can deliberately retain them. [14][29]
- **Visuals and picking.** Collision changes do not cut the rendered mesh. `Part.RayCastEgoSubPart` reads `MeshViewModule` geometry, so visual picking can still hit a surface removed only from collision. Visual geometry, collision geometry, and part picking need to agree if the feature presents a visible cut. [30]
- **Persistence and restoration.** Store the geometry recipe or durable generated assets, not transient Bepu handles. Rebuild through normal loading and cleanup paths. Sphinx's saved placements already reconstruct native resources from retained source identity. [23]

Replacing the entire vessel collider with a top-level `Mesh` would avoid the nested-mesh issue, but it is a considerably broader integration. `ConstraintSim.UpdateShape` distinguishes `BigCompound` from a fallback `Compound`; `TryGetContactOffset` also assumes one of those compound types. The part-contact mapping relies on the `BigCompound` layout. A top-level vessel mesh would need those assumptions and its update, animation, ownership, and contact attribution behavior revisited. It is therefore not equivalent to Sphinx's comparatively isolated static mesh path. [13][27]

Flattened triangle children are another theoretically possible representation because Bepu exposes `Triangle` and KSA already uses triangle children for terrain. But stock part XML exposes no triangle template, and replacing a proper mesh with many independent triangle leaves changes surface-contact behavior and cost. It is a separate mod experiment, not the preferred path over a compact convex decomposition. [1][3][31]

**Why deleting contacts is not general subtraction.** KSA's callbacks can reject pairs, reject child tests, or modify contact manifolds. Existing code uses filtering for collision avoidance and unwanted terrain backface recovery. That makes selective noncollision possible, but it does not solve CSG. [24]

Consider a ball inside a cylindrical bore cut through a box. Correct collision needs contacts against the bore's inward-facing wall. The original solid box test never represented that wall. Removing some box contacts cannot create its missing positions, normals, and depths; treating the cutter as another ordinary solid pushes in the wrong direction. Simply reversing selected normals does not recover the missing manifold either. This is the central geometric limitation explained by the maintainer's CSG discussion. Limited ghost regions may be useful for some gameplay, but they should not be described as reliable solid subtraction. [9]

Bepu is extensible: the bundled narrow phase has collision and sweep registries with public registration methods. A custom shape and custom pair tests could therefore be investigated. General analytic subtraction would still require shape bounds, consistent surface contacts across relevant shape pairs, ray queries, continuous-motion handling where used, resource management, and integration with KSA's compound and part mapping assumptions. The presence of registration APIs proves an extension mechanism, not an available CSG implementation. [32]

**Terrain cuts are a separate problem.** A hollow static placed over planetary ground does not subtract the ground underneath it. KSA generates its terrain collider separately, including triangle patches and a coarse supporting box. A below-ground tunnel would require coordinated terrain collision and rendering changes, beyond making one part or static hollow. [31]

**Recommended next decision.** For a hollow vessel part, first author a small set of boxes or individually convex hull meshes and use the existing collider template path. For a hollow body-fixed building, prepare a mesh containing the desired openings and interior walls and use Sphinx's explicit Mesh mode within its limits. For an eventual interactive subtraction tool, generate those same supported outputs when the geometry changes. A custom analytic Bepu CSG collider has a much larger research and maintenance cost than either approach.

Before calling a future implementation complete, native acceptance should demonstrate passage through the opening, contact against each interior wall and rim, expected blocking of an oversized probe, stable resting and sliding contacts, and behavior under relevant speeds and rotations. Vessel tests should include scaling, animated subparts, detachment, and correct contact-part attribution. Static tests should include bubble transitions, origin snaps, removal of a supporting surface, and save/load. Those are proposed checks; this report does not claim they were run.
